IDENT - test results for this release (QEMU 8.2: PIIX3, CMD646, SiI3112)

bin\NT\ident.sys was built from these sources with i686 MinGW (GCC 13)
against import libraries generated from NT 3.1's own SCSIPORT.SYS and
NTOSKRNL.EXE exports; it imports nothing NT 3.1 lacks. src\NT\build.bat
(MSVC 4.0 + NT4 DDK) builds the same sources. For the Windows 95 tests
bin\9X\IDENT9X.MPD was built from the same sources with MinGW as well
(PE layout as from MSVC: file and section alignment 200h);
src\9X\build.bat builds the same sources with MSVC.
bin\2KXP\i386 and bin\2KXP\amd64\ident.sys were built with MinGW
(i686 / x86_64) against import libraries generated from Windows 2000's
and XP x64's own SCSIPORT.SYS, NTOSKRNL.EXE and HAL.DLL; src\2KXP (DDK
build) builds the same sources.

QEMU used for the tests
- QEMU 8.2.2 (-M pc: PIIX3 IDE in compatibility mode, 8086:7010,
  programming interface 80h; -M q35: no IDE function at all), patched
  (test environment only):
  - ATA disks with 1024/2048/4096-byte logical sectors (IDENTIFY words
    106/117-118) on the IDE bus.
  - The PIIX3 function reporting another device ID (ICH4 24CB) for the
    Intel timing-register path.
  - The CMD646 (1095:0646) PCI IDE controller built into the x86
    targets: native mode on both channels (programming interface 8Fh),
    one PCI INTA for both channels (level-sensitive, shared).
    SeaBIOS writes the legacy addresses 1F0h/3F4h/170h/374h into BAR 0-3
    of every native IDE function, which would make it decode the same
    ports as the PIIX3; with CMD646_BARS=e000 those writes are moved to
    E000h/E010h/E020h/E030h, as a BIOS that assigns free I/O space would
    do. Bus master (BAR 4) as SeaBIOS assigned it.
  - CMD646_STICKY=1: the CMD646 interrupt latches stay set until
    software writes 1 to them (CFR/ARTTIM23 in config space, MRDMODE
    bits 2/3 at bus master base + 1), and the PCI interrupt follows the
    latches, as on the real chips. Stock QEMU drops a latch when the
    drive drops INTRQ, which hides the problem.
  - CMD646_DEVID=0643/0648/0649[:rev]: the CMD646 model reports another
    member of the family (or revision).
  - IDE_PCI_DEVID=<vendor>:<device>[:<revision>]: the PIIX3 function
    reports another vendor/device (unknown controller, ALi M5229,
    RZ1000, CMD640, ServerWorks OSB4); its registers stay PIIX3's.
  - IDE_SIMPLEX=1: the bus master status reports bit 7 (simplex).
  - The SiI3112 model (1095:3112, class 0104, BAR 5 registers with
    SIEN) built into the x86 targets.
- QEMU's bus master is an SFF-8038i engine with PRDs; UDMA/MWDMA
  timing registers are accepted but have no effect on speed. The
  "modes" the driver reports (MWDMA 2 on PIIX3, UDMA 5 on ICH4) are
  what SET FEATURES and the timing registers were programmed to.
- Tools (sources in the tools folder of the work tree, not shipped):
  idetest (GET_INFO, SMART, pass-through, MODE SELECT, VERIFY,
  START STOP UNIT, power IOCTL), bench (QD32 4K write/read, 50 MB
  sequential verify by CRC), sumtool (CRC of a directory tree),
  secdump (sector dump), geom (geometry/capacity per drive), devstat
  (device node status, 2000/XP), hiio (64 KB write/read/compare at any
  offset of a raw disk, with a page-aligned buffer and with buffers
  2 and 6 bytes off a dword boundary).

Windows NT 4.0 SP6 (x86)
- System disk on AHCI (AHCINT), IDE data disks through IDENT:
  primary master 512-byte disk, primary slave 4096-byte disk (data),
  secondary master CD-ROM, secondary slave 1024-byte disk. One adapter
  per channel (IRQ 14 and IRQ 15), both interrupt-driven, MWDMA 2.
  idetest on every disk: GET_INFO, SMART (VERSION, IDENTIFY, ENABLE,
  READ ATTRIBUTES, RETURN STATUS), READ CAPACITY, ATA PASS-THROUGH(12)
  IDENTIFY, PASS-THROUGH(16) CK_COND descriptor sense, REPORT LUNS,
  MODE SENSE/SELECT caching page (write cache off and on), SYNCHRONIZE
  CACHE, VERIFY(10)/(16), START STOP UNIT stop/start, read after
  standby: all OK. bench on three volumes: RESULT OK, 0 errors
  (QD32 4K ~6-7 MB/s, verify ~110 MB/s). sumtool over the data disks
  matches the host-side CRC. Interrupt counts in GET_INFO rise with
  the I/O (flags 5: interrupt path, bus master).
- The same with the MPS HAL and 2 CPUs (IOAPIC): all OK, 0 errors.
- Boot from IDE: system disk moved to the PIIX3 primary master, atdisk
  disabled, IDENT boot start, scsidisk/disk Start=0: boots, idetest
  and bench OK. Disk Administrator sees every disk.
- ICH4 (24CB) device ID: UDMA 5 selected (cable 80), timing registers
  programmed, all tests OK (modes 25).
- DMA=0 in DriverParameters: every device PIO 4 (modes 04), 0
  interrupts, all tests OK (QD32 4K ~3-5 MB/s, verify ~6 MB/s).
- IRQ=0: Fast Polling with DMA (flags 4, ints 0), all tests OK.
- ISA tertiary channel at 1E8h/3EEh, IRQ 11 (QEMU isa-ide): found in
  the ISA pass, PIO (no bus master), interrupt-driven, data disk
  formatted and verified; the PCI channels unaffected.
- q35 without any IDE function: DriverEntry returns C00000C0 (no
  adapter), the system boots on, no hang. The same when the IDE
  function has no device on either channel: no targets, boot
  continues.
- Earlier builds: the PCI bus-master enable was never written on NT 4.0
  (DMA status 05, PRD reads FFh) - fixed by writing the command
  register through CF8h/CFCh on the whole NT build; Disk Administrator
  with that build zeroed sector 0 of the data disks (MBRs rewritten).

Windows 2000 SP4 (x86)
- Controller in compatibility mode (PIIX3, PnP): the first builds
  failed IRP_MN_START_DEVICE (Device Manager code 10; scsiport.sys
  logs IO_ERR_INCORRECT_IRQL because the resource list carries no
  interrupt). With the IRP_MJ_PNP front end (idepnp.c) IRQ 14 is
  added to the start resources: "PnP start: 1 list(s), 2
  descriptor(s), interrupt missing" / "IRQ 14 added (vector 151,
  IRQL 5)", the adapter starts with both channels (the primary
  interrupt-driven, the secondary Fast Polling), devstat reports
  problem 0 for the node. Appending IRQ 15 as well made ScsiPort take
  15 as the adapter's interrupt, so only 14 is appended.
- System disk on AHCI, IDE data disks 512/4096/1024 bytes and CD-ROM
  through IDENT: idetest all OK, bench RESULT OK 0 errors on every
  volume (100 MB), sumtool CRCs match, chkdsk finds no problem on the
  512-, 4096- and 1024-byte volumes.
- Hibernation (VGA=cirrus; the std VGA without a driver makes Windows
  refuse S3/S4 on its own): with the data disks on IDENT, hibernate
  and resume, bench and CRC afterwards OK. With the system disk on the
  PIIX3 through IDENT (boot through IDENT, atapi detached from the
  node): hibernate writes through the dump instance ("channel from
  its IRQ at 1F0"), resume OK, data verified; a second hibernate
  cycle OK.
- INF ranking: PCI\CC_010180 (a hardware ID of the PIIX3 function)
  outranks the in-box PCI\CC_0101 and VEN_8086&DEV_7010 matches, so
  Update Driver with ident.inf takes the node from atapi/intelide and
  keeps it; the disks need no new driver (SCSI class driver in-box).
- A PCI function whose decoders pci.sys turned off after a failed
  start (seen with earlier builds, every register FFh) is re-enabled
  by the driver (I/O space, bus mastering) before the next command.
- PIO on the 4096-byte disk (DMA=0): READ SECTORS with 512-byte DRQ
  blocks (QEMU hands the data out in 512-byte blocks whatever the
  logical sector size), verified; the earlier 4096-byte block
  transfer failed with status 58.

Native (enhanced) mode, IRQ other than 14/15 - CMD646, CMD646_BARS=e000

- Windows NT 3.1 (system disk on AHCI, data1 on the CMD646 primary, the
  1024-byte disk t1k on the secondary): IRQ 10. Default: flags 4,
  0 interrupts - Fast Polling with UDMA 5, as documented for a native
  function on NT 3.1. With DriverParameters IRQ=1: flags 5, interrupt
  counts 52/83 after idetest. Both runs: idetest RESULT OK fails=0,
  bench RESULT OK errors=0, sumtool CRC lists of both volumes identical
  between the two runs.
- Windows 2000 SP4 (system disk on AHCI, CD on the PIIX3, k512 on the
  CMD646 primary, k1024 on the secondary): the start-device resources
  of the CMD646 are 11 descriptors with 5 port ranges and 1 interrupt
  (IRQ 11); the hook leaves them alone, both channels interrupt-driven,
  UDMA 5, device node problem 0. The PIIX3 in the same boot: 2
  descriptors, 1 port range, no interrupt -> IRQ 14 added as before.
  idetest RESULT OK fails=0 on both disks (flags 5, ints rising),
  bench RESULT OK errors=0, chkdsk clean, the CRC lists of the two
  volumes identical to each other and to the PIIX3 run.
  This run found a defect in the shipped 2000/XP binaries: GCC took
  the PartialDescriptors[1] declaration inside CM_RESOURCE_LIST's
  List[1] literally and compiled the descriptor scans of idepnp.c to
  look at descriptor 0 only. The CMD646's interrupt (descriptor 1 or
  later) was not seen, IRQ 14 was added, and the start failed with
  code 10 (IRQ 14 belongs to the PIIX3). The descriptors are now
  reached through a byte offset, and IRQ 14 is added only to a list
  with no interrupt and at most one port range. PIIX3 compatibility
  mode re-tested with the fixed binary: all tests OK, CRCs identical.
- Windows XP x64 (F6 text-mode setup, system disk on the CMD646 primary,
  CD on the PIIX3): the CMD646 starts with its own resources, IRQ 10,
  both channels interrupt-driven, UDMA 5. Partition, format, file
  copy, first boot from the CMD646 disk (SeaBIOS boots the native
  controller at E000h), the installed system loads IDENT on IRQ 10
  again, GUI-mode setup reaches Regional Options; no DMA error and no
  fall-back to Fast Polling in the log (debug build of the fixed
  source on the F6 disk; the shipped x64 binary is the same source
  without the log output).
- Windows 95 (system disk on the PIIX3 through IDENT9X, w512 on the
  CMD646 primary): the new CMD646 was matched to IDENT9X.INF by
  PCI\VEN_1095&DEV_0646 and installed from C:\IDENT without a restart
  prompt (driver key hdc\0001). FindAdapter: "2 channel(s) at E000",
  IRQ 10, UDMA 5. Default Fast Polling: w95io 64 MB RESULT OK errors=0,
  sumtool CRC list of D: unchanged across the run. With
  "AdapterSettings"="IRQ=1" in hdc\0001: "IRQ 10/0, interrupt", both
  channels interrupt-driven, w95io RESULT OK errors=0, no fall-back to
  Fast Polling.

Controller families, chip errata and safety rules
(NT 4.0 runs: system disk on the PIIX3 through IDENT, debug build with
the decisions logged to COM2; "modes" from GET_INFO: 0x = PIO, 1x =
MWDMA, 2x = UDMA, 8x = ATAPI)
- Negative control for the CMD64x latch: the binary shipped before
  this change, NT 4.0, CMD646 with CMD646_STICKY: the boot stops in the
  kernel phase; QEMU counts 42,317,400 interrupts on the slave PIC
  cascade (IRQ 2) with IRQ 11 held - an interrupt storm. With this
  release the same setup boots; the latch is cleared on every
  interrupt and command.
- CMD646 rev 7 (646U2), sticky latches, native mode at E000h/E020h,
  IRQ 11: UDMA 2 (the chip's limit; the driver programs ARTTIM/DRWTIM/
  UDIDETCR), both channels interrupt-driven (flags 5, interrupt counts
  as without the latch), idetest RESULT OK fails=0, bench RESULT OK
  errors=0 on four volumes. (The native-mode runs above were made
  before the CMD timing code and kept the BIOS mode, UDMA 5.)
- CMD648 (CMD646_DEVID=0648), sticky: latch cleared at bus master
  base + 1; UDMA 4; all tests OK. CMD643: MWDMA 2 (no UDMA); all OK.
- SiI3112 (class 0104, programming interface 00): the bus master at
  BAR 4 was not recognised before (only the programming interface was
  looked at), and the adapter failed altogether: NT 4.0 refuses the
  uncached extension to a PCI adapter without a DMA object. Now: BAR 5
  mapped, SATA interrupts masked, transfer mode register set, UDMA 5,
  interrupt-driven on IRQ 11. Data disk with model ST320012AS:
  "15 sectors per command (Silicon Image 3112 errata)", requests split;
  bench RESULT OK errors=0 on it, idetest OK.
- Unknown controller (IDE_PCI_DEVID=8086:7777, no BIOS DMA flags as
  SeaBIOS sets none): every device PIO 4 ("controller timing unknown"),
  all tests OK, hiio OK. Same with DMA=1: disks UDMA 5, CD UDMA 2
  (40-conductor cable); hiio's buffers 2 and 6 bytes off a dword
  boundary are refused by the PRD builder ("cannot build PRDs") and the
  requests run with PIO instead of failing - data verified.
- ALi M5229 rev C4 (IDE_PCI_DEVID=10B9:5229:C4) with an empty 150 GB
  disk: without DMA=1 all PIO (no BIOS flags); with DMA=1 disks UDMA 5,
  the CD PIO 4 ("no ATAPI DMA on this controller"); hiio at 140000 MB
  (LBA 286,720,000, above 2^28: the 48-bit commands go with PIO on
  this revision) aligned and misaligned: 0 bytes differ. Checked with
  QEMU's ide_bus_exec_cmd trace: on that disk 3 READ SECTORS EXT (24h)
  and 3 WRITE SECTORS EXT (34h), the three hiio passes, and no READ/WRITE
  DMA EXT (25h/35h); everything below 2^28 went as READ/WRITE DMA
  (C8h/CAh).
  (A first attempt used big.raw, whose NTFS partition above LBA 2^28
  has 4 KB file records; NT 4.0's NTFS stops with 0x50 mounting it,
  also on the plain PIIX3 - a file system limit, not the driver.)
- Simplex (IDE_SIMPLEX=1, PIIX3): primary channel MWDMA 2, secondary
  channel (CD, data disk) PIO 4 with no interrupts; all tests OK.
- RZ1000 (1042:1000) and CMD640 (1095:0640) identities: read-ahead
  turned off (RZ1000: config 40h bit 13, read back), both channels in
  one adapter ("channels 2"), Fast Polling (flags 4, ints 0), PIO;
  all tests and hiio OK.
- ServerWorks OSB4 (1166:0211) with DMA=1: disks MWDMA 2 instead of
  UDMA, the CD UDMA 2; all tests OK.
- Windows 2000, CMD646 (sticky) and SiI3112 in one machine, both on
  IRQ 11: CMD646 UDMA 2, SiI3112 UDMA 5 (BAR 5 from the PnP
  resources); idetest OK on the 512-, 1024- and 4096-byte disks, bench
  OK, chkdsk clean, the CRC lists of the three volumes identical.
  Reinstalling the driver on the running CMD646 failed its restart
  (code 10) before: the new instance found the channels in the claim
  table the previous one left. A PnP start now takes its function's
  channels regardless; reinstalled twice in one session, problem 0.
- Windows 95: CMD646 (sticky) and SiI3112 found as new hardware and
  installed from C:\IDENT; CMD646 UDMA 2 with Fast Polling (the 9x
  rule for the 643/646), SiI3112 BAR 5 mapped with _MapPhysToLinear,
  UDMA 5; w95io 32 MB RESULT OK errors=0 on both, the CRC lists of the
  other files unchanged.

In-box IDE drivers turned off at installation
- NT 4.0, oemsetup.inf run as the SCSI Adapters applet runs it
  (setupdll loaded as legacy.inf does): atapi Start 3 -> 4 and atdisk
  -> 4, the old values kept as InboxStart_atapi/InboxStart_atdisk under
  the IDENT key, a second installation keeps the first saved values;
  removal puts atapi back to 3 and deletes the saved values.
  Removal did nothing before: legacy.inf does not set
  STF_WINDOWSSYSPATH, so the driver file was looked for in "\drivers"
  and taken as absent (the same check in GetInstalledOptions and before
  copying). The INF now gets the directory from setupdll
  (GetWindowsNtSysDir) when it is empty.
- NT 3.1, same INF: atdisk Start 1 -> 4 (atapi does not exist and is
  skipped), scsidisk Start 0; removal puts atdisk back to 1.
- Windows 2000, ident.inf through UpdateDriverForPlugAndPlayDevices:
  atapi, pciide, intelide Start 4; viaide (not part of Windows 2000)
  created with Start 4 only; CriticalDeviceDatabase\pci#cc_0101 ->
  IDENT, class SCSIAdapter.
- XP x64, F6 text-mode installation from floppy_amd64 onto a disk on a
  CMD646 (sticky latches) with a SiI3112 data disk and the CD on the
  PIIX3: GUI-mode setup ran ident.inf (handed over by txtsetup.oem) for
  the three controllers; read from the installed SYSTEM hive at Regional
  Options: atapi, pciide, intelide, viaide, cmdide, aliide Start 4,
  IDENT Start 0, CriticalDeviceDatabase\pci#cc_0101 -> IDENT. A reset at
  that point booted again through IDENT (CMD646 UDMA 2, SiI3112 UDMA 5,
  PIIX3 CD MWDMA 2) with the in-box drivers off; GUI-mode setup went on.
- NT 4.0, text-mode case (txtsetup.oem writes only IDENT's own key), the
  driver turning the in-box drivers off itself, debug build, system disk
  on the PIIX3:
  1. atapi and atdisk at Start 4, no saved values: the first start saves
     InboxStart_atapi = 4 and InboxStart_atdisk = 4, nothing else.
  2. Saved values deleted, atapi Start 0 (as text-mode setup leaves it
     when it installs atapi too): atapi takes the channels at boot and
     IDENT's adapters are refused (C0000018, conflicting addresses); the
     driver still sees the controller, saves InboxStart_atapi = 0 and
     sets atapi Start 4.
  3. Next boot: IDENT has both channels, MWDMA 2, no registry change.
  4. atapi set back to Start 3 by hand: left at 3 on the following boot
     (a saved value exists).
  The first attempt found nothing written: ZwOpenKey failed, as NT 4.0
  rejects OBJ_KERNEL_HANDLE (a 2000-and-later attribute); NT builds now
  open keys without it.
- NT 3.1, the same (system disk on AHCI, IDENT for the PIIX3 disks):
  atdisk at Start 1 and no saved value: the boot runs with both drivers
  enabled and works; IDENT saves InboxStart_atdisk = 1 and sets atdisk
  Start 4; the next boot has IDENT alone, no further change. A key named
  disk (Type 1, Start 4, no image) exists on this NT 3.1 installation;
  the class driver step first set it to Start 0 too (the INF did the
  same). Now only scsidisk is set when it exists (disk only where there
  is no scsidisk, NT 4.0), in the driver and in oemsetup.inf.
- oemsetup.inf after this change, run as before on NT 4.0 and NT 3.1:
  NT 4.0 disk Start 0; NT 3.1 scsidisk Start 0, disk left at 4; the
  saved values written by the driver at its boot are kept by the
  installation, removal on NT 3.1 put atdisk back to the saved value and
  deleted it. NT 4.0 removal with InboxStart_atapi set to 3: atapi back
  to 3, both saved values deleted, IDENT Start 4 (deleted at the next
  boot). With IDENT still a boot driver, removal first asks for
  confirmation ("marked as a boot device"), Cancel being the default;
  Cancel leaves everything as it was (setup exit code 2).
- NT 3.1 load order: with the IDENT key given Tag 40 (as txtsetup.oem
  and oemsetup.inf write it), IDENT loads before AHCINT, which has the
  system disk; IDENT's first disk becomes \Device\Harddisk0 and
  multi(0)disk(0)rdisk(0) points to it: the boot ran autochk and then
  stopped with the system disk idle. The same with IRQ=0 DMA=0, and
  with the old binary; with nvme2k tagged ahead instead of IDENT the
  boot stops with 0x7B. A disk numbering matter of NT 3.1, described in
  the README; the runs above use the IDENT key without Tag.

Memory above 4 GB
- hmtest (new tool): physical memory report, then 64 KB, 8 KB and
  512-byte writes and reads from and into places spread over a large
  buffer (all of it touched first), buffers page-aligned and 2 and 6
  bytes off a dword boundary (those go with PIO); every read compared.
- XP x64, 3 GB RAM of which 2 GB above the 4 GB line (QEMU
  max-ram-below-4g=1G): Windows reports 3071 MB, highest page 17FFFF.
  From the GUI-mode setup command prompt (Shift+F10, the 32-bit tools
  under WOW64), debug build: hmtest with a 768 MB buffer, 300 rounds,
  on a PIIX3 disk and on the SiI3112 disk: 0 reads differ; 7200
  "cannot build PRDs" lines, exactly the misaligned requests of the two
  runs, so no aligned request fell back because of an address above
  4 GB. Shorter runs with 768 MB and 1400 MB buffers and hiio: all OK.
  A temporary build that looked up the physical address of every data
  buffer handed to the driver (MmGetPhysicalAddress) counted 14336
  requests, none with the buffer above 4 GB, also with a 1400 MB buffer
  that cannot fit into the 1 GB below 4 GB: XP x64's ScsiPort gives a
  32-bit bus master buffers below 4 GB, so PIO into a buffer above
  4 GB does not come up there. (6 GB of RAM could not be run: the test
  machine's memory limit stopped QEMU.)
- Windows 2000 Professional, /PAE with ntkrnlpa.exe, 3 GB RAM of which
  2.5 GB above 4 GB: Windows uses 511 MB (highest page 1FFDF), as
  Professional uses no memory above 4 GB; IDENT runs normally with the
  PAE kernel (hmtest 300 rounds, hiio, idetest, bench, chkdsk all OK).
  Memory above 4 GB under Windows 2000 needs Advanced Server or
  Datacenter, not tested.

  INT 13h and NTLDR read 512-byte sectors; NTLDR hangs or reports
  ntoskrnl.exe missing. Such disks work as data disks only.
- Windows 2000 refuses S3/S4 while the std VGA adapter has no driver
  (VgaSave); with the Cirrus adapter and its driver S3 and S4 are
  offered. Not related to IDENT.
- After a hibernation test that was cut short, Windows 2000 asks
  whether to delete the restoration data; deleting hiberfil.sys clears
  it.
